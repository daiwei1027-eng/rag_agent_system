# Day20：怎样使用这 40 条 TinyStories 问题

## 当前交付

- `tinystories_queries_draft.jsonl`：40 条英文问题、实际 chunk ID、参考答案、逐字证据、问题类别与草稿状态。
- `tinystories_annotation_review.md`：便于人工阅读和逐条复核的版本。
- `tinystories_eval_manifest.json`：记录语料 SHA-256、语料规模与采样方法。语料内容变化时应复核标注。

40 条覆盖 13 条事实、11 条原因、8 条同义改写、8 条多个条件问题。类别用于组织这次标注，没有经过独立难度验证。

这是标注草稿。所有证据摘录已在源文本中验证；包含同一完整证据片段的其他 chunk 也已加入。逐字匹配无法找全只包含部分证据或采用另一种表述的相关 chunk，所以不能把目前的列表视为完整 gold。尚未运行检索实验或计算指标。

## 相关性规则

对于本轮问题，一个 chunk 如果能独立提供该问题的完整答案，就标为相关。仅有人名、相同主题、问题中的部分关键词，不足以标为相关。参考答案用于指导判断，评估时比较 chunk ID，不按答案字符串做精确匹配。

本轮不设计必须联合多个 chunk 才能回答的问题；`relevant_chunk_ids` 中多个 ID 表示多个可以独立回答问题的证据，而非必需拼接的证据部件。

## 逐条复核

1. 阅读标注中的证据及其完整 chunk，确认不是另一篇故事或仅有同名人物。若问题本身有歧义，先修改问题。
2. 阅读相邻 chunk。语料有重叠与故事边界拼接，相邻 chunk 可能包含另一份充分答案。
3. 在全库搜索关键情节，如 `needle` 与 `button`；人物名只能作为辅助条件。查阅其他候选是否也能回答相同问题。
4. 可把 FAISS Top20 与 reranker 排序结果合并为候选池辅助复核，但不能把排名或分数直接当成相关性标注。应保留直接阅读源文本得到的正例，避免漏掉两组系统均未召回的证据。
5. 对新发现的相关 chunk 补 ID 和证据，删除不充分的正例。人工复核后把 `annotation_status` 改为 `reviewed`。该状态代表完成这套复核步骤，不代表已数学证明全库相关性完备。
6. 固定一版标注后，让 baseline 与 reranker 使用完全相同的标注。若补充标注，应重新计算两组指标并记录版本。

## 接入评估脚本

评估脚本至少读取 `query_id`、`query`、`relevant_chunk_ids`；其余字段用于复核与分析。chunk ID 是字符串，例如 `"0"`。这份文件为 JSONL，每行一个独立 JSON 对象。

每个问题召回一次 Top20，再比较原排序与重排顺序。两组均评估 Recall@1/3/5、HitRate@1/3/5 与 MRR@20；MRR@20 必须基于完整 20 条排序，因此评估重排时要保留 Top20，不能只保留配置中的 Top5。Recall@20 用于观察召回上限。

Recall@k = 前 k 条中相关 ID 的数量 / 标注相关 ID 的总数。

HitRate@k = 前 k 条至少有一个相关结果则为 1，否则为 0。

RR@20 = 前 20 条中第一个相关结果的位置倒数；没有则为 0。MRR@20 为各问题 RR@20 的平均值。

Recall 对漏标敏感，也会受重叠 chunk 数量影响。例如同一答案存在两个相关 chunk，Top1 命中一个时 Recall@1 为 0.5，但 HitRate@1 为 1。一起报告两种指标，避免将证据副本召回率误解为问题回答成功率。

## 能得到什么结论

这些问题由阅读选中的语料片段后设计，主要衡量“能否找回已知可回答问题的证据”。不是实际用户流量的代表样本，也不是通用问答能力评估。

可以先复核 5 条，检查指标函数和检索流程，再完成 40 条。若需要调参，可按故事分组划分开发集与测试集，例如 30/10；同一故事的改写问题不要分到两边。10 条测试问题很小，单次命中率变化 0.10 就可能只对应一条问题，不能据此宣称普遍提升。

逐问题保留 baseline / reranker 的排名、首个相关位置、指标变化和失败原因。最终表中的数字全部由实验产生，不填预设的提升数字。

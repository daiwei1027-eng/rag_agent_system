# RAG Agent System — 阶段一：本地 Qwen Agent 接入（进行中）

日期：2026-10-10

## 本次目标与结果

沿用现有手写 Agent Loop 和工具注册表，接入本地 Qwen，让真实模型完成一次「请求工具 → 执行工具 → 读取 observation → 最终回答」的闭环。目前已用 `calculator` 跑通；`time` 和真实文档检索尚未接入 Agent 运行入口，因此阶段一还未验收完成。

## 实现与设计取舍

- `agents/llm_client.py` 中的 `LocalLLMClient` 复用本地模型和 tokenizer，使用 Qwen 的 chat template 渲染消息与工具 schema，只解码新生成的 token。`chat()` 将 `<tool_call>` 中的 JSON 转成内部 `id / name / arguments` 结构；普通回答保持 assistant 消息结构。
- 适配器现在区分无工具标签的普通回答、完整的一个或多个工具调用，以及标签缺失或顺序不匹配的错误输出。后者抛出 `ValueError`，避免把残缺调用当作最终回答。工具名称和参数结构也在解析后校验。
- `agents/models.py` 定义统一的 `AgentResult`：`status`、`answer`、`trace`、`error`。`trace` 是本次运行的完整消息历史，其中工具 observation 序列化在 `role=tool` 消息的 `content` 中；无需另建一份内容重复的事件列表。模型调用步数和工具调用次数仍可按需要从消息历史计算，未作为返回字段保存。
- `agents/loop.py` 对直接回答、模型结构错误、重复调用和步数耗尽使用同一返回结构。有工具调用时继续执行循环；只有收到非空的最终回答才返回 `completed`。模型解析抛出的 `ValueError` 转为 `model_error`。

## 真实运行证据

运行 `scripts/run_agent.py` 后，模型加载成功，进程退出代码为 0。消息顺序与关键内容如下：

```text
user: 请使用 calculator 计算 12 × 8，并根据工具结果回答。
assistant tool_call: call0, calculator, {"operation": "multiply", "a": 12, "b": 8}
tool observation: {"tool_call_id": "call0", "name": "calculator", "ok": true, "result": 96}
assistant: 计算结果是 96。
```

这证明真实模型发起了工具调用，Agent 执行了真实 calculator，结果进入下一轮模型输入，最终回答使用了 96。运行脚本逐条打印 `trace` 后又打印了整个列表，所以控制台出现重复展示；这不是重复执行。

## 检查与排错

- 用户运行 `python -m pytest -q tests/test_local_llm_client.py`：**5 passed in 12.09s**。覆盖本地模型产生 calculator 调用、适配器区分工具调用与直接回答，以及缺少开头或结尾标签的错误路径。
- 此前调整 Loop 分支后运行 `python -m pytest -q -p no:cacheprovider tests/test_agent_loop.py tests/test_tool_registry.py`：**71 passed in 0.21s**。该结果发生在本次适配器标签修复之前，覆盖 Agent Loop 与工具注册表，不代表全项目测试通过。
- 主要返工点是早期 `Agent.run()` 的返回契约未统一：成功时直接返回 assistant 消息，停止时返回状态字典。加入完整轨迹和错误路径时，不同分支必须重新梳理。统一结果结构后，修正了无工具调用与工具调用分支的返回位置；问题不是 calculator 计算错误。

## 真实运行结果

| 场景 | 关键证据 | 结果 |
|---|---|---|
| `direct` | trace 只有 user → assistant；没有工具 observation | 直接回答水的化学式为 H2O |
| `tinystories` | search_documents 返回 3 条重排文段，`chunk_id=0` 排第一 | 回答 `Lily`，并输出 `依据：chunk_id=0` |
| `tinystories_auto` | 问题未指定工具名；模型自主调用 search_documents，返回 `chunk_id=0` | 回答 `Lily`，但最终文字漏写 chunk_id |
| `calculator` | calculator 的 `ok=true, result=96` | 最终回答 96 |
| `time` | time 使用 `timezone_name=Asia/Shanghai`，结果带 `+08:00` | 最终回答使用工具时间 |
| `multi_tool` | 同一轮请求 time 和 calculator；两条 observation 均 `ok=true` | 最终回答同时使用时间和 96 |
| `tool_failure` | calculator 对除数 0 返回 `ok=false`、`ValueError` | 最终明确说明无法计算，没有编造数值 |

七次任务级 `status` 均为 `completed`。`tool_failure` 的工具级 `ok=false` 与任务级 `completed` 不矛盾：模型收到失败 observation 后给出了明确解释。保存文件已重新读取核对：七份 JSON 均可解析，模型请求中的消息快照与 trace 前缀一致，工具 observation 和上述结果对应。

## 设计与排错

- 检索工具先从 FAISS 召回配置数量的候选，再由 CrossEncoder 重排并返回模型请求的 `top_k` 条。每条结果固定包含 `chunk_id`、`text`、向量 `score`、`source`、`rerank_score` 和 `rerank_rank`；未重排时后两项为 `null`，避免返回结构随配置变化。
- 初次在未指定工具名的 TinyStories 问题上，模型直接声称无法访问资料库。将工具描述写清楚为“可检索本地 TinyStories”后，它开始自行选择检索；另一版英文提示曾使模型连续生成过多工具调用并在 token 上限处截断，适配器按残缺标签返回 `model_error`。最终使用“如需检索，只提出一次简短英文查询”的问题，得到一次成功检索和正确答案。这说明工具选择与调用数量仍受提示和模型能力影响。
- Windows 控制台曾在打印含特殊字符的文段时发生编码异常。脚本现先写 JSON 再打印，并对无法编码的控制台字符使用转义替代；UTF-8 文件保存原始字符。
- 记录文件保留模型接口输入（messages 和 tools）及规范化响应，未保存 tokenizer 渲染后的完整 prompt、模型原始 token 序列、索引文件哈希或各轮耗时。绝对路径也与当前机器有关，尚不能称为跨机器的逐位复现。

## 阶段二：固定协议与正式检索基线

本次先固定 `docs/stage2-evaluation-protocol.md`，再完成阶段二任务 2 的检索基线。核心题集校验、正负例分组、逐题计算、记录与计时由用户逐步实现，助手审查并完成路径、入口等机械性整理。尚未执行固定 12 题的 Agent 端到端基线；以下指标均为检索指标，不是答案准确率或 Agent 成功率。

### 原理与固定口径

- 唯一正式题集为 `data/benchmark/tinystories_queries.jsonl`，manifest 版本 `day21-stage1-v1.2`；45 条 reviewed 记录，40 条可回答、5 条指定故事范围内不可回答。旧草稿不参与实验。
- 依据人工标注的 `answerable` 分组，并检查它与相关 ID 非空状态是否一致。正例未检索到证据仍是正例；负例可能检索到对应故事，但故事没有问题要求的信息。
- 每题仅用 FAISS 召回一次 top-20，同一份候选用于无重排排序和 CrossEncoder 重排，均保存完整 20 条排序。报告 Recall@1/3/5、HitRate@5、MRR@20。
- Recall 的题内分母是该题标注相关 ID 数，汇总采用 40 题宏平均；HitRate@5 是命中题数 / 40；MRR@20 是 40 个 RR@20 的均值。q041–q045 相关 ID 为空，排除并记录 `unanswerable_no_relevant_ids`，不将其作为零分混入平均。
- 配置为 `all-MiniLM-L6-v2` Embedding、归一化开启，`ms-marco-MiniLM-L6-v2` CrossEncoder，max_length=512、batch_size=8。配置文件中同时记录的 Qwen、temperature、generation token 上限未参与本次纯检索计算。

### 核心实现与排错

`scripts/eval_retrieval.py` 已改为读取正式题集，检查 ID 唯一性、reviewed 状态、布尔类型、标注一致性以及 45/40/5 数量；先完成分组，再只遍历 40 条正例进行评估。相关 ID 转成集合，两个 RR 输入显式截断到前 20 条。

用户实现过程中修正了三个关键问题：负例条件不能写成“不可回答且相关 ID 非空”；分组循环与评分循环不能嵌套，否则会重复评分；评分循环必须重新从当前 item 读取 query 和相关 ID，否则 Python 会保留上一循环最后一题的变量，造成题目与结果错配。

记录分别保存逐题结果、汇总 JSON、排除记录、指标 CSV 和配置。`summary` 仅保留两组指标，继续供 CSV 遍历；另用 `summary_record` 包装计数、加载与预热信息。修正了曾将汇总误写入 `per_query.json` 的问题，逐题结果与汇总现在分别写入两个文件。

非 Notebook 的两个评估脚本中剩余 5 处机器专属路径已清理。运行目录从项目根目录解析，创建时 `exist_ok=False` 防止覆盖；历史记录中的运行时绝对路径保留。检索脚本装入 `main(argv=None)` 并设置入口保护，导入时不执行评估。直接运行时自动生成北京时间戳目录，也可通过 `--run-dir` 显式指定。Notebook 本次不整理。

题集与 manifest 在模型加载前复制为快照，保存 manifest 版本以及题集、manifest、FAISS、文段文件的 SHA256，并校验题集指纹与 manifest 一致。文件快照使用 `shutil.copy2()`；`deepcopy()` 复制内存对象，不能替代磁盘文件复制。

### 耗时口径

资源是惰性加载，先显式调用两类组件的加载方法并计时，再固定使用 q002 执行一次真实检索和重排预热。预热不加入正式结果；q002 仍在正式 40 题中评分。逐题使用 `perf_counter()`，检索和重排分别计时，JSON 写盘不在逐题计时内。

|---|---:|

### 三例复盘：事实、假设与验证设计

用户按“失败层级 → 原文依据 → 原因假设 → 验证办法”分析以下三题。原文与排序已核对；查询改写和候选扩展目前仅是验证设计，未执行，不将其写成优化收益。

**q029：候选已召回，FAISS 排序靠后，重排纠正。** 问题是熊为什么忍住没有吃森林里的食物。标注 chunk 7000 从第 19 升到第 1；原文写明 `he realized that it was poison` 与 `resisted the temptation to eat it`，正确答案是发现食物有毒，而不是已经中毒。FAISS 第一名 chunk 7072 也包含熊、探索和食物，却讲熊吃浆果，不支持该因果。用户提出向量检索可能更重视共同主题、未充分区分动作与因果条件。验证设计是仅将 `resist eating` 改为 `not eat`，保留其他限定条件，观察 chunk 7000 的 FAISS 名次；不向查询加入答案 poison，也不能仅凭一次名次改善断定模型不理解某个词。

**q007：候选召回遗漏。** 问题是 Max 跑开后谁一起滑下并拥抱。正确 chunk 1500 明确写出 Max 跑开，随后 Ben 和 Lily 一起滑下并拥抱；两组第一名 chunk 4443 讲 Lily 和 Max 等待大男孩离开滑梯，缺少目标事件。Max 是背景事件的人物，不是问题要求的滑下并拥抱者。chunk 1500 未进入 top-20。用户提出人物、滑梯主题相似可能掩盖事件条件；候选范围也可能限制召回。后续可保持原查询与模型不变，只扩大候选到 50，再视结果决定是否诊断到 100，记录正确文段名次和重排后的前 5 命中情况。

**q038：候选召回遗漏。** 问题限定猫把鸟直接带去向另一只动物求助。正确 chunk 9250 中，猫负责带鸟求助，猫头鹰负责检查翅膀与给药，鸟接受治疗。两组第一名 chunk 5552 是 Lily 与兽医治疗鸟的另一篇故事，主题和部分治疗行为相似，但角色关系不符；正确 chunk 9250 未进入 top-20。用户提出检索可能没有充分区分主体与事件链，验证设计与 q007 相同：只改变候选数并检查正确文段是否进入候选、是否被重排到前 5。

“候选未召回”是已验证的现象，“top-20 不够大”仍是假设。扩大候选后若标注证据出现，才支持候选范围限制的判断；若仍不出现，单纯扩大范围尚不足以解决问题；若出现但重排仍靠后，则另有排序问题。候选扩展还需要计量额外重排成本。本次正式基线保持候选数 20，不因提出优化方案改写原结果。

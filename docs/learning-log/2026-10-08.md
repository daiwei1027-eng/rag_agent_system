## 执行异常与恢复

`execute()` 仍校验请求和参数、执行 handler，并允许异常向外传播。`execute_safe()` 捕获普通 `Exception`，将失败包装为包含调用 ID、工具名、`ok=False` 和错误信息的 observation，不包含 `result`。不捕获 `BaseException`。

失败 observation 通过 tool 消息回传给模型；下一轮模型可以请求修正后的参数、其他工具，或再次尝试。程序本身没有增加自动重试。

- 未知工具和错误参数在 handler 执行前拒绝；执行记录只包含合法调用。
- `RuntimeError` 在 handler 内产生；先记录一次失败执行，再验证下一次成功执行。
- 工具主动抛出的 `TimeoutError` 与执行层等待到期分别验证，不能把主动抛异常当作有限等待的证据。
- 同一轮某个工具失败不会阻止后续合法工具；跨轮案例验证错误确实进入下一次模型输入。

## 真正的有限等待

`execute_safe(..., timeout_seconds=None)` 沿用同步路径。传入期限时，使用 `ThreadPoolExecutor(max_workers=1)` 提交一次 `self.execute`，通过 `future.result(timeout=timeout_seconds)` 限时等待。

等待到期返回 `TimeoutError` observation；其他普通异常保留实际类型和信息。`finally` 中使用 `shutdown(wait=False, cancel_futures=True)`，避免清理阶段再次等待正在运行的工具。

`Agent` 构造参数 `tool_timeout_seconds` 使用仅限关键字的形式，保存后传给每次工具执行。`None` 表示不限制等待；其他值必须是有限正数，拒绝 bool、错误类型、零、负数、NaN 和正负无穷值。Agent 构造阶段和 registry 独立入口均保留配置校验。

阻塞测试使用 `threading.Event`：`started` 表示工具已启动，`release` 控制何时继续，`finished` 表示阻塞工具结束。调用返回时检查已启动且未完成，在测试 `finally` 中释放工具并有限等待清理。Agent 集成案例验证第一次仍阻塞时，第二次无外部副作用的 calculator 调用能成功，最终返回回答。

## 连续重复调用与步数预算

重复签名为工具名与 `json.dumps(arguments, sort_keys=True, ensure_ascii=False)`。忽略调用 ID，参数字典键顺序变化也不能绕过检测。调用 ID 仍负责将执行结果对应回具体请求。

`max_repeated_calls` 默认为 2，必须是正整数且排除 bool。连续相同请求第 1、2 次允许执行，第 3 次在执行前返回停止结果。不同调用出现后计数重置为 1；签名和计数是 `run()` 的局部状态，不跨运行累积。同轮和跨轮的连续调用都计入限制。

该机制不检测所有循环。交替的 A → B → A → B 由 `max_steps` 兜底。`max_steps` 限制模型调用轮数，不是工具次数或总耗时；一轮可以执行多个工具。最后允许的一轮若直接回答则成功返回；若仍请求工具，执行后返回预算耗尽。

## Fallback 与返回结果

fallback 是停止后的兜底策略，上限是触发条件。当前策略由程序直接返回明确状态和未完成说明，不再调用模型，也不编造任务结果。

| 停止条件 | status | answer |
|---|---|---|
| 连续相同请求超过阈值 | `repeated_tool_call` | 工具调用连续重复，已停止，任务尚未完成。 |
| 模型轮数耗尽，仍未给出答案 | `max_steps_reached` | 已达到最大模型调用轮数，任务尚未完成。 |

停止结果还包含 `steps`：重复停止记录当前模型调用轮数，预算耗尽记录 `self.max_steps`。工具 observation 是单次执行结果，Agent 停止结果是整个运行的结果；两者不能混用。成功路径仍返回 assistant 消息，尚未统一所有返回类型。

## 排错与学习要点

1. `pytest.raises` 验证异常，不会制造异常；故障 handler 应主动 `raise`。
2. 同步工具结束后检查 `perf_counter()` 只能发现事后超时，不能停止等待。直接调用内部函数也不会产生并发。
3. `executor.submit(self.execute, tool_call)` 传入函数和参数；不要先在当前线程执行函数。
4. 标准库 `Future.result` 的参数名是 `timeout`，右侧可以使用项目变量 `timeout_seconds`。误写后出现的 TypeError 通过 observation 的 message 定位。
5. Event 是对象，用 `is_set()` 检查状态，不与布尔值做身份比较。阻塞测试必须释放后台任务。
6. NaN 不等于自身，非有限值使用 `math.isfinite()` 检查。可选配置先处理 None，再检查类型和值。
7. 当前调用签名必须在比较前生成；不同调用时更新上次签名并重置计数。工具执行留在内层循环，预算耗尽返回放在外层循环之外。
8. 构造校验测试只构造 Agent；异常块外检查模型未被调用，避免运行阶段异常让测试假通过。

## 当前局限

- FakeLLM 修正请求和回答是预设的，只证明控制流程，不证明真实模型能自主纠错。
- 线程超时只停止等待，不能终止已运行 handler。后台任务可能继续产生副作用；不能无条件重试。每次超时创建的后台线程可能累积，尚无共享并发预算或进程隔离；进程退出也可能等待这些线程。
- 默认超时为 None；模型调用没有超时控制，max_steps 也不是整个运行的时间或工具次数预算。
- 连续重复规则可能阻止合法的第三次相同查询；参数语义等价但 JSON 表示不同的请求未必被识别。交替循环仅通过模型轮数兜底。
- 签名生成发生在 registry 校验前；缺少 name/arguments 或参数不可序列化的请求仍可能直接报错。模型响应结构、输出大小与结果序列化尚未完整处理。
- 普通异常捕获也会包装内部程序错误，应保留诊断信息。尚未增加持久化执行日志、每轮耗时或完整运行配置快照；学习日志不能代替运行日志。
- 成功结果与停止结果的结构不同。重复拦截可能发生在一轮工具请求的中途，返回时历史只保留本次局部内存，尚无完整轨迹输出。

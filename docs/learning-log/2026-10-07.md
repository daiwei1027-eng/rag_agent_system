# RAG Agent System — Day23 Handwritten Agent Loop

日期：2026-10-07

## 完成目标

在 Day22 工具执行层基础上，用户亲手实现最小 Agent：模型响应 → 工具执行 → observation → 再次调用模型。没有使用 LangChain 或 LangGraph，保持“先手写，再 LangGraph”的学习顺序。

本次使用 FakeLLM 提供预设响应，使用真实 calculator handler 验证执行与结果回传。尚未接入真实模型，也未在 Agent 中验证真实文档检索或时间工具。

## 文件与职责

| 文件 | 职责 |
|---|---|
| `src/rag_agent_system/agents/loop.py` | LLMClient 接口协议、Agent 初始化和运行循环 |
| `src/rag_agent_system/agents/__init__.py` | agents 包入口 |
| `src/rag_agent_system/tools/registry.py` | 复用 Day22 的 schemas 导出与 execute_safe 执行入口 |
| `tests/test_agent_loop.py` | FakeLLM、输入快照记录、Agent 行为测试 |

LLMClient 使用 Protocol 声明 chat(messages, tools) 接口。它提供类型契约，不执行运行时协议校验，也不要求实现类显式继承该接口。

## 循环与停止条件

```text
校验 question → 创建本次运行的局部 messages → 获取工具 schemas
    ↓
调用 LLM → 保存完整 assistant 消息
    ├─ 无 tool_calls → 返回 assistant 响应
    └─ 有 tool_calls → 按顺序逐个 execute_safe
                         ↓
                    包装并追加 tool 消息
                         ↓
                    下一轮调用 LLM

模型调用轮数用尽 → 返回 max_steps_reached
```

max_steps 默认为 5，必须是正整数，使用 type(max_steps) is int 排除 bool 和其他类型。question 必须是字符串，拒绝空字符串和纯空白；当前校验使用 strip()，但消息保留原输入文本。

max_steps 限制模型调用轮数，不是工具执行次数。一个模型响应可以请求多个工具，程序按请求顺序执行全部工具。最后允许的一轮若直接回答，正常返回；若仍请求工具，当前实现执行该轮全部工具后返回耗尽状态，没有额外模型调用。

耗尽结果：

```json
{"status": "max_steps_reached", "answer": null, "steps": 1}
```

成功路径直接返回 assistant 消息字典；耗尽路径返回状态字典，当前两种返回结构尚未统一。

## 请求、Observation 与消息历史

模型工具请求使用项目内部协议：id、name、arguments。其中 arguments 是已经解析的字典；具体模型 API 的格式转换和 JSON 参数解析尚未实现。

execute_safe 返回成功或失败 observation。Agent 将它序列化为字符串，再包装成对话消息：

```python
{
    "role": "tool",
    "tool_call_id": observation["tool_call_id"],
    "content": json.dumps(observation, ensure_ascii=False),
}
```

外层 tool 消息标记角色和调用归属，内层 observation 描述执行结果。成功包含 ok=True、result；失败包含 ok=False、error，不包含 result 字段。调用 ID 对应模型原请求。

单工具案例在第二轮调用模型时，输入快照是 user → assistant 工具请求 → tool 结果。最终 assistant 回答在第二轮返回后才被追加，因此不在第二轮输入快照中。同轮两个工具则对应两个独立 tool 消息。

工具失败处理沿用 registry：execute_safe 捕获 TypeError 和 ValueError；它不是任意异常捕获或隔离执行机制，其他异常仍会向外传播。

## FakeLLM 与测试设计

FakeLLM 顺序返回预设 assistant 响应，call_count 记录已返回的响应数量。工具执行和消息追加不增加该计数。预设响应耗尽时抛出 RuntimeError，与 Agent 的轮数耗尽状态分别处理。

message_history 保存每次 chat 的 messages 深拷贝，避免后续列表追加改变早先输入快照。实际实现先记录快照再检查响应耗尽，因此失败调用也可能增加历史记录，但不会增加 call_count。

包装 calculator 的 recording_calculator 记录真实 handler 参数。多工具测试检查完整 calls 列表，以验证执行次数、参数和顺序；模型调用次数由 fake.call_count 单独验证。

| 工具除零失败 | 1 | ValueError、nonzero 信息、无 result 字段、错误回传后继续回答 |

## 排错与学习要点

1. 返回 response 是返回当前消息；返回 self.responses 会返回完整列表，返回 self.responses[-1] 会跳过前面的工具请求。
2. list.append 原地修改列表并返回 None，不能把返回值当作更新后的列表，也不能嵌套 append，否则历史会出现 None。
3. 模型 response 已是完整 assistant 消息，直接 append；再次包装进 content 会错误嵌套并隐藏 tool_calls。
4. 保存 assistant 工具请求后，再保存其 tool 结果；不能直接把裸 observation 追加进对话历史。
5. 轮数耗尽返回放在外层循环结束后，避免最后一轮仅执行第一个工具就提前退出。
6. message_history 外层索引表示模型调用，内层索引表示该次输入中的消息；第二次输入的第三条消息是 message_history[1][2]。
7. tool_call_id 是字符串，再索引 [0] 会得到字符；同轮两个结果应分别读取两个 tool 消息。
8. 失败结果没有 result 字段，应断言 "result" not in observation；访问 observation["result"] 会触发 KeyError。
9. 构造配置校验测试只在 pytest.raises 内创建 Agent，避免混入 run 导致异常来源不明确。
10. 旧 RAG PromptBuilder 假定已有 context；Agent 初始阶段尚未检索，不能直接沿用“上下文不足就回答不足”的完整流程。证据不是指令等规则可在后续适配时复用。

## 当前局限与下一阶段

- FakeLLM 的工具请求与最终回答均为预设，只能验证控制流程、消息传递和工具执行，不能证明真实模型会正确选择工具或理解结果。
- 尚未验证模型响应结构、tool_calls 类型、调用 ID 唯一性、内容有效性和 JSON 序列化失败；没有工具调用时直接返回，不能保证非空或正确答案。
- max_steps 不是工具次数、耗时或资源预算；没有工具超时、输出大小限制和执行隔离。
- 输入快照仅在测试中记录，核心 Agent 尚未保存持久化执行日志、每轮耗时或真实运行配置。
- 同一 Agent 连续运行案例需要补消息历史断言；多轮工具链、未知工具、真实搜索及时间工具的 Agent 集成尚未覆盖。
- 文件仍有未使用导入、已完成 TODO 注释和格式整理空间，今天保留用户实现，未额外修改核心代码。
- 下一阶段先检查现有生成器与目标模型的工具调用能力，再设计真实 LLM 适配层；适配层负责消息与工具 schema 转换、参数解析，核心循环继续复用。

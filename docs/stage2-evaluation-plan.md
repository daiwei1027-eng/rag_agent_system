# 阶段二任务：建立可复现的检索与 Agent 评估基线

日期：2026-10-12。预计 **10–14 个有效小时**；以验收条件为准，不以脚本或测试数量判断完成。

## 目标与边界

阶段一已经证明本地 Qwen → Agent Loop → 工具 → observation → 最终回答能够运行。阶段二回答另一个问题：**在固定问题集上，它做得怎样，时间花在哪里，错误发生在哪一层？** 先固定输入、配置和评分口径，再运行基线与分析失败案例。不要把阶段一的七条演示轨迹当作成功率，也不要用 `status=completed` 代替答案正确。

本阶段复用现有 TinyStories 标注集、FAISS、CrossEncoder 和 Agent；不引入新的数据库、评估平台或 Web 框架。暂不做后端服务化，也不在看到第一条失败后反复改提示词。优化方案可以写入结论，留给下一阶段按基线结果排序实施。

## 任务顺序

### 1. 固定评估协议（约 2 小时）

- 以 `data/benchmark/tinystories_queries.jsonl` 为**唯一正式题集**：45 条已复核记录，40 条可回答、5 条故事范围内不可回答。`data/archive/evaluation/historical/root/tinystories_queries_draft.jsonl` 是旧草稿，不能混入正式结果。记录 benchmark manifest、模型和索引版本、配置、运行环境、评估日期。
- 检索指标在 40 条可回答题上计算；5 条无相关 chunk ID 的负例不参与 Recall/MRR 的分母。固定候选数、最终条数与 `k`，同一批 FAISS 候选用于有/无重排比较。建议候选 20、比较排序前 20、报告 Recall@1/3/5、HitRate@5、MRR@20，并写清这些指标各自的分母。
- Agent 端到端先固定下面 12 条案例，运行前不要按结果挑选：`q001, q003, q005, q006, q007, q015, q022, q038, q040, q041, q042, q045`。包含事实、因果、改写、多条件与 3 条不可回答题。提示词应告诉模型回答 TinyStories 问题、尽可能引用依据；不要在题目中点名 `search_documents`，这样才能观察自主工具选择。保存统一提示词模板。
- 先写人工判定表：答案是否正确、是否有工具返回的直接证据、引用 `chunk_id` 是否出现在工具结果且对应标注证据、负例是否明确说证据不足。缺引用要单列为失败；`completed` 只说明任务级流程结束。对于措辞不同但语义正确的答案，保留人工判断和理由；不要用简单字符串相等伪装答案准确率。

**验收：**正式题集、子集 ID、提示词、参数、判定规则和分母都写在同一份运行协议中，之后的实验按该协议执行。

### 2. 检索基线（约 3–4 小时）

- 检查并整理 `scripts/eval_retrieval.py`：它目前读取绝对路径的**草稿**文件并写固定输出位置。改为读取正式题集，输出到一次运行专属目录；保留逐题的基线排序、重排排序、相关 ID、指标和汇总。
- 在相同 40 条可回答题上比较 FAISS 与 FAISS+CrossEncoder。记录 5 条负例被排除的原因。核对输出条数、`k`、相关 ID 类型与已有 `evaluation.metrics` 的定义；不能把重排分数和 FAISS 分数直接比较大小。
- 将差异最大的几个题目回溯到原文段，区分“候选未召回”与“候选已召回但排序靠后”。

**验收：**一份可重跑的逐题文件、一份汇总表，以及至少 3 个有原文证据的错误分析。指标不要求达到预设数值。

### 3. Agent 端到端基线（约 3–4 小时）

- 基于 `scripts/run_agent.py` 的装配和记录方式，批量运行固定 12 题；保留每题完整 `AgentResult`、模型请求、工具调用、observation、最终文本、配置和时长。已有 `run_agent.py --all` 仅运行七个演示场景，不能直接充当这 12 题评估。
- 在同一套问题和提示词上比较开启与关闭重排（至少形成一组明确的基线和一组对照）。确保除重排开关外，其余配置、题集和评分口径一致。模型权重加载与首题预热应与稳定推理耗时分开记录；小样本报告每题耗时和中位数即可，不必使用不稳定的 p95。
- 对每题标注：有没有自主选择检索、检索是否返回相关文段、回答是否正确、是否有证据支撑、引用是否正确、不可回答题是否拒答，以及非 `completed` 的终止状态。统计时展示分子/分母，并区分“未调用工具”“证据没找到”“有证据但没引用”“答案编造”等原因。

**验收：**两组运行均有可读的逐题记录与同口径汇总；能够定位至少一个从检索结果到最终回答的失误，而不只给出一个总准确率。

### 4. 复盘与收尾（约 2–4 小时）

- 将结果写入 `docs/learning-log/`：指标表、代表性成功/失败轨迹、误差来源、耗时口径，以及接下来最值得修的一项问题。记录“标注未覆盖全部相关文段”“45 题未拆训练/测试集”“12 题是固定小样本”等局限；不要把本地演示结论外推为线上效果。
- 只为新评估计算或真实发现的缺陷补必要的测试；复用现有 `tests/test_metrics.py` 等覆盖，避免堆相似测试。运行相关检查并如实写下通过项及未运行项。
- 完成时能够在面试中解释：为什么检索与端到端分开评估、为什么负例不用 Recall、为什么 `completed` 不等于正确、如何保证有/无重排比较公平，以及下一步如何根据错误分布选择优化对象。

**阶段二完成条件：**固定协议、正式题集上的检索基线、固定子集上的 Agent 基线和对照、逐题记录、可复核的结论全部齐备。无需通过某个预设成功率门槛。下一阶段再根据基线处理主要瓶颈，然后考虑服务化。

## 第一件事

在新对话中先核对正式 benchmark、`scripts/eval_retrieval.py` 和 `scripts/run_agent.py` 的输入输出；完成任务 1 的运行协议，再动评估代码。核心实现与评分标准优先由用户亲手完成；助手可提供骨架、审查与机械性整理。Git 提交和推送由用户完成。
